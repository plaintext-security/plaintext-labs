## Why this matters

You hardened the host in Module 02/03, expressed the baseline as code in Module 06, and scored it as compliant in Module 07. That host was secure *on the day you ran the playbook*. Three months later it almost certainly is not — and nobody touched it maliciously. A routine `apt upgrade` shipped a new default that re-enabled a kernel parameter you'd locked down. An on-call engineer set `PermitRootLogin yes` at 2 a.m. to debug an outage and never reverted it. A new package dropped a config file that loosened a permission. None of these is an attack; all of them are **drift** — the slow, entropic divergence between the state you *declared* and the state the host is *actually in*. The whole thesis of this track is "a baseline that is enforced and then drifts," and this is the module that owns the drift directly. "Set and forget" is the failure mode: a control you apply once and never re-check rots silently, so that by the time an auditor (or an attacker) finds the re-opened root login, it has been open for ten weeks and you had no idea.

The reason drift is dangerous rather than merely annoying is that it is *invisible by default*. A misconfiguration that was never there is loud — your hardening playbook fails, your scan flags it, you fix it. A misconfiguration that *appears later*, after everything went green, makes no noise at all: the host runs fine, users don't complain, and the control silently stopped doing its job. The skill that separates a hardening *project* from a hardening *program* is the one this module builds: detecting that t=0-fine / t=30-wrong divergence the moment it happens, knowing exactly *which control* drifted and *what* changed, pulling the host back to baseline automatically, and being told about the delta — so the re-opened root login is closed within an hour of the 2 a.m. change, not discovered ten weeks later in an audit.

## Objective

Take a host already hardened to a baseline-as-code, **declare** that baseline explicitly, then **introduce real drift** (a package update that flips a sysctl, an operator who re-opens `PermitRootLogin`, an added world-writable file), and build the **full steady-state loop**: a *scheduled* detector that diffs observed state against declared state, a **diff that reports what changed and against which control** (not just a pass/fail score), **automated reconciliation** that re-converges the host to baseline, and an **alert on the delta** so a human learns *what* drifted and *when*. The deliverable is the running loop, scheduled, proven by introducing drift and watching it get caught and reconciled.

## The core idea

Drift is the gap between **declared state** and **observed state** as a function of time. Configuration management (Module 06) declares the state: "this host *should* have `PermitRootLogin no`, this sysctl set, this umask, auditd running." At `t=0`, right after you converge the host, observed equals declared and the gap is zero. Then the world acts on the host — package updates, operators, drift from other automation — and the gap opens. The steady-state discipline is a loop with four beats that runs *forever*, not a scan you run once: **detect** (re-measure observed state on a schedule), **diff** (compare it to declared and report the delta), **reconcile** (re-apply the baseline so observed converges back to declared), and **alert** (tell a human *what* changed, because a drift that auto-heals silently hides the fact that something keeps re-breaking it). The mental model is the same one a thermostat uses: declare the target, continuously measure the actual, and correct the difference — except here the "actual" is your security posture and the corrections are auditable.

The single most important design judgment in this loop — and the thing most teams get wrong — is the **diff must report *what* changed and against *which control*, not just a score.** Module 07 gave you a compliance *score*: "94/100, you dropped two points." That number tells you that you drifted but not *how*, and a score that goes from 94 to 92 is almost useless operationally — you can't act on it. The drift loop's output has to be a *delta*: "`/etc/ssh/sshd_config:PermitRootLogin` changed from `no` to `yes` (control CIS-5.2.10) at the 03:00 check; `net.ipv4.conf.all.rp_filter` changed from `1` to `0` (CIS-3.3.7) — both reconciled." This is the difference between a smoke detector that beeps and a panel that says *which room is on fire*. Tooling makes this directly available and you should use the native mechanism rather than re-inventing it: Ansible's **`--check --diff`** mode reports exactly which tasks *would* change and shows the before/after lines (a pending change in check mode *is* a drift); OpenSCAP re-scans against the SCAP/CIS content and produces a per-rule pass/fail with the rule ID; osquery lets you *query* observed host state (the actual `sshd_config` line, the live sysctl, the SUID set) as data you can diff. The same "compare declared to observed, report the named delta" pattern is what AWS Config does in the cloud (continuous evaluation against config rules, flag the noncompliant resource) and what `terraform plan` does for IaC (compare prior state to real infrastructure, propose the change set) — drift detection is one idea wearing many tool-shaped hats.

The hard judgment that turns this from a script into a real control is **reconcile-vs-alert: not every drift should be silently auto-healed, and not every drift is a security event.** The naive loop just re-runs the enforcement playbook on a cron and calls it done — but that has two failure modes. First, **auto-reconciling silently hides a recurring cause**: if a nightly package job keeps re-enabling the sysctl and your loop keeps quietly fixing it, you've built a control that masks the real problem (the package job) instead of surfacing it — the *alert on the delta* exists precisely so a human sees "this same control drifted three nights running" and goes fixes the upstream cause. Second, **some drift is legitimate** — an approved change that hasn't yet made it into the declared baseline. The discipline is: the declared state in git is the source of truth, so an *approved* change is a change to the *baseline* (a reviewed commit), not a manual edit on the host; a manual edit on the host that diverges from git is drift *by definition* and gets reconciled. This is exactly the Module-11 lesson one layer over: re-baselining over a change is only safe when you *decided* that change was approved first. Auto-reconcile the clearly-mechanical drift (a flipped sysctl, a re-opened root login — re-converge and alert); for higher-risk classes, alert-and-hold for a human. The loop's value isn't that it heals everything automatically; it's that *nothing drifts silently*.

## Learn (~3.5 hrs)

**Detecting drift with the tools you already have (~1.5 hrs)**
- [Ansible — *Validating tasks: check mode and diff mode*](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_checkmode.html) (~30 min) — the official reference for `--check` (simulate, change nothing) and `--diff` (show the exact before/after lines a task *would* change). This is the engine of your drift detector: a pending change in `--check --diff` against your Module-06 baseline *is* drift, named down to the line. Read it for how to make modules report cleanly and how `ansible_check_mode` lets you skip tasks that can't run safely in check mode.
- [osquery — *Configuring an osquery deployment* (scheduled query packs)](https://osquery.readthedocs.io/en/stable/deployment/configuration/) (~30 min) — read the **schedule** and **packs** sections. osquery turns observed host state into SQL you can diff: the live `sshd_config` value, current sysctls, the SUID set, running services. A scheduled pack is *continuous* observation, and the doc's "only the result-set difference is logged" behavior is drift detection built into the tool — it logs the *change*, which is exactly the delta you want.
- [OpenSCAP Base — oscap compliance scanning](https://www.open-scap.org/tools/openscap-base/) (~30 min) — the open-source SCAP scanner. Where Ansible `--check` diffs against *your* playbook, `oscap` re-evaluates the host against a standard CIS/STIG profile and emits a per-rule pass/fail *with the rule ID*. Read it for the "verifiable, repeatable scanning" framing — re-running the same SCAP content on a schedule and diffing yesterday's pass-set against today's is a control-named drift report.

**The same idea in the cloud and in IaC — drift is universal (~1 hr)**
- [AWS Config — *What Is AWS Config?*](https://docs.aws.amazon.com/config/latest/developerguide/WhatIsConfig.html) (~30 min) — read "Ways to Use AWS Config," especially **Rules and conformance packs** and **Remediation**. This is your exact detect-diff-reconcile-alert loop as a managed service: Config *continuously evaluates* resources against rules, flags the noncompliant one (the diff), can *remediate* (reconcile), and notifies via SNS (alert). Read it to see that the host loop you're building and cloud posture management are the same pattern — it generalizes the skill to the cloud track.
- [Terraform — *terraform plan* command reference](https://developer.hashicorp.com/terraform/cli/commands/plan) (~30 min) — `terraform plan` compares the prior state to the *real* infrastructure and proposes the change set to make them match. That gap *is* drift (someone changed a resource in the console), and `plan` reports it as a named, per-resource diff before any apply. Read it as the IaC sibling of `ansible --check --diff`: declared-vs-observed, reported as a reviewable delta.

**Why "set and forget" fails — the steady-state mindset (~1 hr)**
- *Re-read your own Module 06 lab* — the [Configuration Management lab](../06-configuration-management/lab.md) ends with `--check` flagging a deliberately drifted setting and a `drift-check.sh`. That was *one step*; this module promotes it into the *whole loop* — scheduled, with a control-named diff, automated reconciliation, and an alert. Skim it for the playbook and the `--check` mechanics you'll build on, then notice what it *didn't* do: report which control, reconcile automatically, or alert on the delta.
- [AIDE drift, one layer down — your own Module 11 lab](../11-host-boot-integrity/lab.md) (~20 min) — file-integrity monitoring is *drift detection for files*: baseline known-good, re-check on a schedule, report what changed. Re-skim it for the shared discipline that matters most here too — **the reference you compare against must itself be trustworthy** (the AIDE DB off-box; here, the declared baseline in git as the source of truth, not an editable copy on the host). Configuration drift and file drift are the same loop on different state.

## Key concepts

- **Drift = declared state − observed state, as a function of time.** At `t=0` the gap is zero; the world (package updates, operators, other automation) opens it. "Set and forget" is the failure mode — a control applied once and never re-checked rots silently.
- **The loop has four beats and runs forever: detect → diff → reconcile → alert.** A one-time scan is not a drift control; the *schedule* and the *alert* are what make it steady-state.
- **The diff must report *what* changed and against *which* control — not a score.** "94 → 92" is unactionable; "`PermitRootLogin` no→yes (CIS-5.2.10) at 03:00, reconciled" is the control. A smoke detector that says *which room*.
- **Use the native diff mechanism, don't re-invent it.** `ansible --check --diff` (pending change = drift, line-level), `oscap` re-scan (per-rule pass/fail with rule ID), osquery scheduled packs (observed state as diffable SQL). The cloud (AWS Config) and IaC (`terraform plan`) versions are the same idea.
- **Reconcile-vs-alert is the real judgment.** Auto-healing silently *hides a recurring cause* — the alert exists so a human sees "this drifted three nights running" and fixes the *upstream* job. Auto-reconcile mechanical drift; alert-and-hold higher-risk classes. Nothing drifts silently.
- **Git is the source of truth; an approved change is a *commit*, not a host edit.** A manual change on the host that diverges from declared baseline is drift by definition and gets reconciled; a legitimate change is a reviewed change to the baseline first (the Module-11 "re-baseline only over approved changes" discipline).

## AI acceleration

A model is genuinely strong at the *parsing and reporting* half of this loop — turning raw `ansible --check --diff` output or an `oscap` results XML into a clean, control-named delta table ("here are the three rules that drifted, with their CIS IDs and before/after values"), drafting the osquery scheduled-pack queries, and writing the alert-formatting and the cron wiring. That is real leverage on tedium you'd otherwise hand-roll. But the posture is strict because the dangerous instinct is the one a model defaults to: asked to "build a drift loop," it will write a cron job that re-runs the enforcement playbook and reports "fixed" — a loop that **auto-heals everything silently**, which is precisely the failure mode that hides a recurring root cause and lets a security-relevant change get quietly papered over night after night. The judgment the model cannot make for you is the **reconcile-vs-alert decision per control class** (which drift is safe to auto-fix-and-log versus which must alert-and-hold for a human) and **whether a given change is drift or an approved baseline update** — it does not know your change-management context, so it cannot tell that last night's `sshd_config` edit was an authorized 2 a.m. fix that should become a commit, not silently reverted. Make the model draft the diff parser, the queries, and the alert format; **you** decide what auto-reconciles versus alerts, you confirm the alert *always* fires on a delta (so nothing heals invisibly), and you own that the declared baseline in git — the thing every check compares against — is the real source of truth, edited only by reviewed commit. AI authors the report; you own the policy.
